============================================================
CORE PRODUCT PRINCIPLE
============================================================

DO NOT DESIGN A GENERIC ADMIN DASHBOARD.

The Trainer Dashboard is a professional operational workspace.

A trainer should be able to open the dashboard and immediately understand:

1. What training activities are happening?
2. How are my trainees progressing?
3. Which trainees need attention?
4. How are my courses performing?
5. Are there assessments requiring action?
6. Are there competency gaps?
7. Do I have courses waiting for approval?
8. What actions should I take next?

The dashboard should feel like:

"Training Command Center"

rather than:

"Analytics page with random cards."

40. DATA ARCHITECTURE
============================================================

Dashboard UI must be designed around real API contracts.

Prefer a dashboard aggregation endpoint:

GET /api/trainer/dashboard

Possible response:

{
  "overview": {},
  "courses": {},
  "trainees": {},
  "assessments": {},
  "competencies": {},
  "activity": {},
  "feedback": {},
  "actions": {}
}

Do not make 15 unnecessary API calls when a well-designed aggregation
endpoint can provide the dashboard data efficiently.

However:

Do not create an enormous unmaintainable endpoint.

Separate APIs may be used where independent loading or pagination is needed.

============================================================
53. IMPORTANT: ACTION-FIRST DESIGN
============================================================

Every major dashboard widget should answer one of:

WHAT?
WHY?
WHO?
WHAT NEXT?

Examples:

Metric:
"What is happening?"

Trend chart:
"Is it improving?"

Trainee list:
"Who needs attention?"

Competency:
"Where are the gaps?"

Action panel:
"What should I do next?"

This principle must guide the final composition.

============================================================
54. DO NOT OVERLOAD THE DASHBOARD
============================================================

Not every Trainer feature belongs on the dashboard.

Do NOT place full:
- course builder
- assessment builder
- trainee management table
- resource manager

inside the dashboard.

The dashboard provides overview and entry points.

Dedicated pages handle deep workflows.

============================================================
56. SECURITY UI
============================================================

Never expose Admin actions in Trainer UI.

Do not show:

Manage Users
Manage Roles
Approve Trainers
Organization Administration
System Settings

unless explicitly authorized.

The frontend must hide unavailable actions,
BUT backend authorization remains the source of truth.

============================================================
57. DEMO / PLACEHOLDER RULE
============================================================

The dashboard may visually demonstrate future features,
but distinguish:

LIVE
from
COMING SOON

Example:

[Live]

My Courses

[Coming Soon]

AI Training Insights

Never blur the distinction.

============================================================
58. FINAL UI QUALITY CHECK
============================================================

Before completing the dashboard ask:

Can a trainer understand their situation within 10 seconds?

Can they identify:
- important metrics?
- trainees needing attention?
- course issues?
- pending assessments?
- competency gaps?
- next actions?

If not, redesign the hierarchy.

FINAL DESIGN PHILOSOPHY
============================================================

Capacity Connect Trainer Dashboard should communicate:

"Your training operation, at a glance."

Not:

"Here are many charts."

The dashboard should guide the trainer through:

SEE
↓
UNDERSTAND
↓
IDENTIFY
↓
ACT
↓
IMPROVE

SEE:
training and learner status

UNDERSTAND:
performance and trends

IDENTIFY:
at-risk trainees and competency gaps

ACT:
review, create, assess, improve

IMPROVE:
use feedback, analytics, and future AI capabilities

Build the UI as a scalable product system, not a one-off page.
